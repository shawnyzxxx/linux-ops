## 一、NFS 基础认知：先搞懂「是什么」

### 1.1 定义

NFS（Network File System，网络文件系统）是 Linux/Unix 系统中常用的网络文件共享协议，允许一台服务器（NFS 服务端）将本地文件系统「共享出去」，客户端通过网络将共享目录「挂载到本地」，实现「像访问本地文件一样访问远程文件」。

### 1.2 核心价值

- **解决多台服务器文件共享问题**：如 Web 集群共享静态资源（图片、CSS）、数据库集群共享配置文件，避免每台机器重复存储。
- **简化管理**：只需在 NFS 服务端更新文件，所有客户端即可同步获取，无需逐台机器操作。
- **跨系统兼容**：支持 Linux、Unix、macOS，Windows 需额外配置（如安装 NFS 客户端）。

### 1.3 NFS 与其他文件共享服务的区别（避免混淆）

| 服务类型 | 核心场景 | 支持系统 | 访问方式 | 关键差异点 |
| --- | --- | --- | --- | --- |
| NFS | Linux/Unix 集群文件共享 | Linux/Unix | 挂载为本地目录（透明访问） | 无「客户端软件」，依赖系统挂载机制 |
| Samba | Windows 与 Linux 互访 | Windows/Linux | 网络邻居 / 挂载目录 | 支持 SMB 协议，侧重跨系统文件交互 |
| FTP | 点对点文件传输 | 全平台 | 客户端工具（如 FileZilla） | 需手动上传 / 下载，不支持「透明访问本地目录」 |

这三个服务的典型应用场景：

- **NFS（网络文件系统）**：适用于 Linux/Unix 集群环境下的文件共享，比如多台 Web 服务器共享静态资源（图片、视频）、数据库集群共享配置文件，或科研集群中多台计算节点共享实验数据，实现「一处存储，多机透明访问」。
- **Samba**：主打 Windows 与 Linux 系统之间的跨平台文件互访。例如企业内网中，Windows 员工电脑需访问 Linux 服务器的共享文件（如财务报表、项目文档）；或 Linux 服务器需挂载 Windows 的「网络邻居」共享目录，实现跨系统的文件协作。
- **FTP（文件传输协议）**：用于点对点的文件传输需求，比如网站管理员通过 FileZilla 将网站源码上传到服务器、企业员工之间传输大体积的设计稿 / 安装包，或对文件传输有「手动控制、明确上传下载动作」需求的场景（如客户向服务商提交资料）。

## 二、NFS 核心原理：搞懂「怎么工作」

这是 NFS 的技术核心，需讲清「数据怎么传输、挂载怎么实现」，避免只知「操作步骤」不知「原理」。

### 2.1 NFS 工作过程

NFS 工作过程如下：

1. **服务端**：NFS 组件向服务端的 RPC 注册端口号 111。
2. **客户端**：RPC 向服务端的 RPC 请求 NFS 的 mount 组件的端口号。
3. **服务端**：回复 NFS 的 mount 组件的端口号给客户端的 RPC。
4. **客户端**：mount 调用 NFS 模块，该模块通过本地 rpcbind 进程向服务端的 NFS 的 mount 模块发起网络请求。

> **核心结论**：NFS 客户端必须依赖本地 RPC 进程（rpcbind）。

### 2.2 底层原理：客户端 RPC 的作用

NFS 本身无独立传输协议，完全依赖 RPC 实现「服务发现 + 端口映射」，客户端 RPC 进程（由 rpcbind 服务提供）的核心功能是：

- **发起端口查询请求**：客户端执行 mount 命令时，本地 RPC 进程会主动向服务端的 rpcbind（监听 111 端口）发送请求，查询服务端 NFS 服务（如 nfsd、mountd）的动态端口号（NFS 服务启动时随机分配端口，需通过 RPC 注册）；
- **接收端口映射结果**：服务端 RPC 返回 NFS 服务的实际端口后，客户端 RPC 将该信息传递给本地 NFS 客户端组件，建立后续数据传输连接；
- **维护通信兼容性**：即使 NFS 服务端口动态变化，客户端通过本地 RPC 可动态适配，无需手动配置端口，这是 NFS 架构灵活性的核心保障。

简单说：客户端 RPC 是「请求发起者 + 结果接收者」，服务端 RPC 是「端口查询服务器」，二者缺一不可，无法跳过客户端 RPC 直接与服务端 RPC 通信。

### 2.3 常见误解澄清

> **误解一：「mount 命令直接向服务端 RPC 请求，无需客户端 RPC」——错误。**
>
> mount 是用户态命令，其底层会调用客户端内核态 NFS 模块，而该模块必须通过本地 rpcbind 进程发起网络请求（用户无需手动操作 RPC，但进程必须运行）。

> **误解二：「所有 NFS 版本都需要客户端 RPC」——存在例外。**
>
> NFSv4 默认使用固定端口 2049，可绕过 RPC 直接连接（需服务端禁用 V2/V3 版本），此时客户端 rpcbind 可关闭；但 NFSv3 及以下版本强制依赖客户端 RPC，否则无法工作。

### 2.4 NFS 依赖的协议与端口

NFS 本身不固定端口，需依赖 RPC（Remote Procedure Call，远程过程调用）协议「动态分配端口」，核心交互逻辑如下：

- **RPC 角色**：作为「端口映射器」，记录 NFS 服务的「功能与端口对应关系」，客户端先通过 RPC 获取 NFS 服务的实际端口，再与服务端通信。
- **RPC 端口**：固定 111（TCP/UDP），客户端首先连接此端口查询 NFS 服务端口。
- **NFS 服务端口**：动态分配（如 2049 是 NFS 旧版本默认端口，新版本由 RPC 分配），但核心功能（如文件读写、挂载请求）的端口会注册到 RPC。

NFS 服务涉及的端口分为固定端口和动态端口两类，具体如下：

**1. 固定端口**

rpcbind（原 portmapper）负责端口映射，固定使用 TCP/UDP 111 端口。客户端需先通过该端口查询 NFS 各组件的动态端口，是 NFS 通信的「入口」。

**2. 动态端口（由 rpcbind 分配，可通过配置固定范围）**

NFS 核心组件（如 nfsd、mountd、rpc.statd、rpc.lockd 等）的端口由 rpcbind 动态分配，默认无固定值。但可通过配置文件指定端口范围（以 RHEL/CentOS 为例）：

- **mountd（处理挂载请求）**：可在 /etc/sysconfig/nfs 中配置 MOUNTD_PORT=xxx 固定端口。
- **rpc.statd（状态监控，用于 NFS 高可用）**：可配置 STAD_PORT=xxx。
- **rpc.lockd（锁服务）**：可配置 LOCKD_TCPPORT=xxx（TCP）和 LOCKD_UDPPORT=xxx（UDP）。
- **nfsd（NFS 主服务）**：一般不建议固定端口，若需可通过内核参数调整，但实际场景中极少操作。

> 简言之，NFS 最核心的固定端口是 rpcbind 的 111，其余组件端口默认动态，可通过配置文件指定固定范围以适配防火墙策略。

**协议栈**：NFS 基于 TCP/UDP 协议，生产环境常用 TCP（可靠传输），避免 UDP 丢包导致文件损坏。

### 2.5 NFS 的「共享 - 挂载」核心逻辑

NFS 的本质是「服务端共享目录 + 客户端挂载目录」，完整交互流程如下：

1. **服务端配置**：NFS 服务端通过 exports 配置文件，指定「共享哪个目录、允许哪些客户端访问、有哪些权限」，并启动 NFS 与 RPC 服务。
2. **客户端查询**：客户端启动 RPC 服务（rpcbind），通过 showmount -e 服务端IP 向服务端 RPC（111 端口）查询「可用的 NFS 共享目录」。
3. **客户端挂载**：客户端执行 mount -t nfs 服务端IP:共享目录 本地挂载点，此时客户端 RPC 会向服务端 RPC 申请 NFS 数据传输端口。
4. **透明访问**：挂载成功后，客户端访问「本地挂载点」的文件，实际是通过 NFS 协议与服务端交互，读写服务端的共享目录文件（用户无感知远程交互）。
5. **卸载**：客户端执行 umount 本地挂载点，断开与服务端的 NFS 连接，本地挂载点不再关联远程目录。

### 2.6 NFS 的权限控制逻辑（易混淆点）

NFS 的权限是「服务端 export 配置权限 + 服务端文件系统权限 + 客户端用户映射权限」的叠加，需明确优先级：

- **服务端 export 配置权限**：最外层控制（如 ro 只读、rw 读写、no_root_squash 保留 root 权限），决定客户端「能否执行操作」。
- **服务端文件系统权限**：基础控制（如共享目录的 rwx 权限），即使 export 配置 rw，若服务端文件本身是 r--，客户端仍无法写入。
- **客户端用户映射权限**：NFS 默认会「压缩客户端 root 权限」（root_squash）——客户端用 root 用户访问时，会被映射为服务端的 nfsnobody 用户（低权限），避免客户端 root 篡改服务端文件；若需保留 root 权限，需配置 no_root_squash（生产环境慎用，有安全风险）。

## 三、NFS 组件架构：搞懂「谁在参与」

讲清 NFS 服务端与客户端的核心组件，为后续实操铺垫（需知道「配置的是什么文件、启动的是什么服务」）。

### 3.1 NFS 服务端核心组件

| 组件类型 | 名称 / 路径 | 核心作用 | 关键说明 |
| --- | --- | --- | --- |
| 服务进程 | nfs-server | NFS 主服务进程，负责处理客户端的挂载、读写请求 | 依赖 rpcbind 提供端口映射 |
| RPC 进程 | rpcbind | 管理 NFS 服务的端口映射，客户端查询端口的入口 | 必须先启动 rpcbind，再启动 nfs-server |
| 配置文件 | /etc/exports | 定义 NFS 共享目录、允许的客户端、访问权限 | 核心配置文件，每行对应一个共享规则 |
| 配置生效工具 | exportfs | 重新加载 /etc/exports 配置，无需重启 NFS | 常用命令：exportfs -rv（重新导出所有共享） |
| 状态查询工具 | showmount | 查看 NFS 服务端的共享列表、客户端挂载状态 | 服务端 / 客户端均可使用，如 showmount -e 192.168.1.10 |

### 3.2 NFS 客户端核心组件

客户端无需启动 nfs-server，只需以下组件即可实现挂载与访问：

- **RPC 进程**：rpcbind（必须启动，否则无法查询服务端 NFS 端口）。
- **挂载工具**：系统自带的 mount 命令（需指定 -t nfs 类型，明确是 NFS 挂载）。
- **卸载工具**：umount 命令（断开 NFS 挂载，注意：挂载点有进程占用时无法卸载，需先杀进程）。
- **自动挂载工具**：autofs（可选，实现「访问时自动挂载、超时自动卸载」，节省资源）。

## 四、NFS 实践操作：从「理论」到「动手」

### 4.1 环境准备（前置条件）

**网络要求**：NFS 服务端与客户端需在同一网段，能互相 ping 通（关闭防火墙或开放相关端口）。

```bash
# 服务端(shawn:192.168.60.128)安装（nfs-server + rpcbind）
yum install nfs-utils -y

# 客户端(fuji:192.168.60.132)安装（仅需 nfs-utils，包含 mount.nfs 工具）
yum install nfs-utils -y
```

### 4.2 服务端配置：共享目录

**步骤 1：创建共享目录并设置权限**

```bash
# 1. 创建共享目录（示例：共享 /data/nfs 目录）
mkdir -p /data/nfs

# 2. 设置文件系统权限（确保客户端能读写，示例：755 允许其他用户读执行，若需写则 777）
chmod 755 /data/nfs
```

**步骤 2：编辑 /etc/exports 配置文件**

exports 格式：共享目录 客户端地址(权限1,权限2,...)。关键参数说明与示例如下。

客户端地址格式：

| 客户端地址格式 | 说明 | 示例 |
| --- | --- | --- |
| 单个 IP | 允许指定 IP 客户端访问 | 192.168.60.129 |
| 网段 | 允许指定网段客户端访问 | 192.168.60.0/24 |
| 通配符 | 允许指定域名后缀的客户端访问 | *.test.com（需 DNS 支持） |
| 所有客户端 | 允许所有客户端访问（慎用） | * |

权限参数与风险提示：

| 权限参数 | 说明 | 风险提示 |
| --- | --- | --- |
| rw | 读写权限 | 需确保服务端目录有写权限 |
| ro | 只读权限 | 安全，适合共享静态资源 |
| root_squash | 客户端 root 映射为服务端 nobody（默认） | 安全，避免客户端 root 越权 |
| no_root_squash | 保留客户端 root 权限 | 高危，可能被篡改服务端文件 |
| no_all_squash | 仅 root 用户被映射，其他用户不会被映射（默认） | 需确保客户端普通用户权限可控，否则可能越权 |
| all_squash | 所有客户端用户（含 root）映射为服务端 nobody | 需确保 nfsnobody 权限合理，避免过度限制或开放 |
| anonuid | 指定客户端用户的 UID | 需确保指定 UID 在服务端存在且权限合理，否则可能权限混乱 |
| anongid | 指定客户端用户的 GID | 需确保指定 GID 在服务端存在，否则组权限可能失效 |
| sync | 同步，同时将数据写入内存与硬盘中，保证数据不会丢失（默认） | 安全，避免断电丢数据 |
| async | 异步，数据先保存到内存，一段时间之后集中写入到磁盘 | 性能高但有丢数据风险 |

示例配置（允许 192.168.60.0/24 网段客户端读写 /data/nfs，同步写入，默认压缩 root 权限）：

```bash
vim /etc/exports
# 添加以下内容
/data/nfs       192.168.60.0/24(rw,sync,root_squash)
```

使配置生效：

```bash
exportfs -ar
```

- 「-a」：导出（或取消导出）/etc/exports 文件中定义的所有共享目录。
- 「-r」：重新导出所有共享目录（逻辑上等价于「先取消所有导出，再重新导出所有」）。

**步骤 3：启动服务并验证**

```bash
# 1. 先启动 rpcbind（NFS 依赖 RPC）
systemctl start rpcbind
systemctl enable rpcbind  # 开机自启

# 2. 启动 nfs-server
systemctl start nfs-server
systemctl enable nfs-server

# 3. 验证共享配置（服务端本地查询）
showmount -e localhost
# 输出类似：Export list for localhost: /data/nfs 192.168.60.0/24，说明共享成功
```

> 若验证不通过，可临时关闭防火墙与 SELinux 排查；生产环境应改为按端口策略放行，而非直接关闭。

### 4.3 客户端挂载：访问共享目录

**步骤 1：创建本地挂载点**

挂载点是客户端的「本地目录」，需先创建（目录需为空，否则挂载后原目录内容会被隐藏）：

```bash
mkdir -p /nfs_client   # 示例挂载点
```

**步骤 2：测试服务端共享（可选但推荐）**

```bash
# 客户端查询服务端的 NFS 共享列表（验证网络与 RPC 连通性）
showmount -e 192.168.60.129   # 192.168.60.129 是 NFS 服务端 IP
# 若输出服务端的 /data/nfs 共享，说明连通正常
```

**步骤 3：执行挂载**

```bash
# 格式：mount -t nfs 服务端IP:共享目录 本地挂载点
mount -t nfs 192.168.60.129:/data/nfs /nfs_client
```

**步骤 4：验证挂载与访问**

```bash
# 1. 查看挂载状态（确认 NFS 挂载成功）
mount | grep nfs
# 输出类似：192.168.60.129:/data/nfs on /nfs_client type nfs (...)

# 2. 测试读写（需服务端配置 rw 权限）
# 客户端创建文件（实际写入服务端 /data/nfs）
echo "test nfs file" > /nfs_client/test.txt

# 服务端验证（查看是否有 test.txt）
cat /data/nfs/test.txt
# 若输出 "test nfs file"，说明读写正常
```

> 说明：本例客户端挂载命令中的服务端 IP 使用 192.168.60.129，实际部署时请按服务端真实 IP 替换。

### 4.4 客户端自动挂载（开机挂载）

手动挂载在客户端重启后会失效，需配置「开机自动挂载」，有两种方式：

**方式 1：通过 /etc/fstab 配置（简单通用）**

```bash
vim /etc/fstab
# 添加以下内容（格式：服务端共享目录 本地挂载点 文件系统 选项 0 0）
192.168.60.129:/data/nfs  /nfs_client  nfs  defaults  0  0

# 验证配置（立即生效，无需重启）
mount -a   # 加载 /etc/fstab 所有配置
```

> 「defaults」包含 rw（读写）、suid、dev 等默认选项，适合大多数场景。

**方式 2：通过 autofs 实现「动态挂载」（进阶，节省资源）**

autofs 会「仅在客户端访问挂载点时自动挂载，超时后自动卸载」，适合非频繁访问的场景：

```bash
# 1. 客户端安装 autofs
yum install autofs -y

# 2. 编辑主配置文件（指定「挂载点目录」与「子配置文件」对应关系）
vim /etc/auto.master
/auto_bendi    /etc/auto.misc
# 添加：/auto_bendi  /etc/auto.misc  # /auto_bendi 是「父挂载点」，/etc/auto.misc 是子配置

# 3. 创建子配置文件（定义「子挂载点」与「NFS 共享的映射」）
vim /etc/auto.misc
client  -fstype=nfs 192.168.60.129:/data/nfs
# 添加：client  -fstype=nfs 192.168.60.129:/data/nfs  # client 是子挂载点（最终挂载路径：/auto_bendi/client）

# 4. 启动 autofs 并验证
systemctl start autofs
systemctl enable autofs

# 访问子挂载点（触发自动挂载）
cd /auto_bendi/client   # 首次访问会延迟 1-2 秒，自动完成挂载
df -h   # 可看到挂载状态
```

**定义自动卸载的超时时间**

```bash
vim /etc/autofs.conf
timeout = 3

# 修改后重启 autofs 生效
systemctl restart autofs
# 再次访问触发生效：cd /auto_bendi/client 或 ll /auto_bendi/client
```

### 4.5 auto.master 配置说明

auto.master 是 Linux 系统中 autofs 服务的核心配置文件，用于定义「自动挂载规则的入口」。其作用是关联挂载点与具体的映射文件（如 /etc/auto.misc、/etc/auto.net 等），当用户访问挂载点时，autofs 会根据映射文件的规则动态挂载对应的文件系统（如本地设备、NFS 共享、CIFS 共享等），闲置时自动卸载以节约资源。

- **格式说明**：核心语法为「挂载点 [映射类型[,格式]:]映射文件 [选项]」，例如「/misc /etc/auto.misc」表示「当用户访问 /misc 路径下的子挂载点时，按 /etc/auto.misc 文件的规则执行自动挂载」。
- **安全选项**：nosuid 和 nodev 是默认安全策略，防止外部存储（如共享目录、光盘）中的恶意文件通过 SUID 提权或设备文件滥用系统权限；若需开放这些能力，需显式指定 suid 或 dev 选项。
- **模块化扩展**：通过 /etc/auto.master.d/ 目录可添加自定义映射文件，实现配置的模块化管理，适合多场景、多服务的自动挂载需求。
- **优先级规则**：若多个映射文件中存在相同的挂载点「键」，则先读取到的条目优先生效，因此配置时需注意文件包含顺序和条目顺序。

原文给出的 /etc/auto.master 注释示例：

```bash
# auto.master 文件示例
# 这是一个「主」自动挂载器映射文件，其格式如下：
# 挂载点 [映射类型[,格式]:]映射文件 [选项]
# 有关格式的详细信息请查看 auto.master(5) 手册页（通过 man 5 auto.master 命令访问）。

# 注意：通过 hosts 映射进行的挂载，默认会使用「nosuid」和「nodev」选项，除非显式指定「suid」和「dev」选项。

# 包含 /etc/auto.master.d/*.autofs 目录下的所有文件
# 若要通过此机制添加额外的映射，你需要配置两项内容：一个 /etc/auto.master.d/extra.autofs 文件
# （使用与 auto.master 文件相同的行格式）
# 以及一个独立的挂载映射文件（例如 /etc/auto.extra 或 auto.extra NIS 映射）
# 该映射文件需在 extra.autofs 文件中引用。

# 如果你已配置 FedFS 并安装了相关二进制程序（无论是作为 autofs 的一部分构建，还是从其他包安装），
# 取消以下行的注释以使用 fedfs 程序映射来访问你的 FedFS 挂载。
#/nfs4  /usr/sbin/fedfs-map-nfs4 nobind

# 若可通过 nsswitch 源找到中央主映射，则包含该映射。
#
# 注意：如果被包含的主映射中存在 /net 或 /misc（如上所示）的条目，那么相同的键（挂载点）只会生效第一个读取到的，即第一个出现的键优先。
```

通过理解 auto.master 的配置逻辑，可高效管理 Linux 系统的自动挂载策略，兼顾资源利用率与访问便利性。

### 4.6 常见问题排查（实操必讲）

实操时易遇到「挂载失败」「权限拒绝」，需讲清排查思路：

**问题 1：showmount -e 服务端IP 失败（客户端查不到共享）**

排查步骤：

- 检查服务端 / 客户端 rpcbind、nfs-server 是否启动（systemctl status 服务名）。
- 检查防火墙是否放行 NFS 与 RPC 端口（服务端需开放 111 端口 + NFS 动态端口，简单测试可临时关闭防火墙：systemctl stop firewalld）。
- 检查 /etc/exports 配置是否有误（如客户端地址格式错误、括号与权限间无空格），可通过 exportfs -rv 查看报错。

**问题 2：客户端挂载成功但无法写入（权限拒绝）**

排查步骤：

- 检查服务端 exports 配置是否有 rw 权限（而非 ro）。
- 检查服务端共享目录的文件系统权限（如 /data/nfs 是否有 o+w 权限，客户端非 root 用户需其他用户写权限）。
- 检查是否触发 root_squash：若客户端用 root 写入，需服务端配置 no_root_squash（但不推荐，建议用普通用户测试）。

**问题 3：客户端卸载失败（device is busy）**

原因：挂载点有进程在占用（如当前目录在挂载点、有程序读取挂载点文件）。

解决：先切换到其他目录（cd /），再执行 umount。

## 五、NFS 进阶拓展：解决「生产环境问题」

这部分提升实战能力，覆盖生产中常用的「安全、性能、高可用」场景。

### 5.1 NFS 安全配置（生产必讲）

默认 NFS 安全性较低，需通过以下配置加固。

**（1）严格限制客户端地址**

避免用「*」允许所有客户端，尽量指定具体 IP 或网段（如 192.168.60.0/24），减少暴露面。

**（2）控制 root_squash 权限**

生产环境优先用 root_squash（默认），客户端 root 映射为 nfsnobody，避免越权。若需客户端 root 操作（如部署系统文件），可仅对特定客户端配置 no_root_squash（如 192.168.60.132(rw,no_root_squash)），而非全局开放。

服务端操作示例：

```bash
[root@server ~]# chmod 755 /share/
[root@server ~]# ll -d /share/
drwxr-xr-x. 2 root root 59 Nov  5 19:22 /share/
```

客户端 root 默认映射到 nobody 用户后，对于服务端 /share 目录，客户端 nobody 具有 r-x 权限，因此删除文件会失败：

```bash
[root@client ~]# rm -rf /bendi/*
rm: cannot remove '/bendi/hehe_file': Permission denied
rm: cannot remove '/bendi/redhat_file': Permission denied
rm: cannot remove '/bendi/root_file': Permission denied
```

**（3）防火墙**

不建议直接关闭防火墙，需开放「RPC 固定端口 + NFS 静态端口」（避免动态端口难以配置防火墙）：

```bash
[root@rhce ~]# firewall-cmd --add-service=rpc-bind --add-service=nfs --permanent
success
[root@rhce ~]# firewall-cmd --list-all
public (active)
  target: default
  icmp-block-inversion: no
  interfaces: ens160
  sources:
  services: cockpit dhcpv6-client ssh
  ports:
  protocols:
  forward: yes
  masquerade: no
  forward-ports:
  source-ports:
  icmp-blocks:
  rich rules:
[root@rhce ~]# firewall-cmd --reload
success
```
